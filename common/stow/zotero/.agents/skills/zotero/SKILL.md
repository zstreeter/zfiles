# Zotero

Zotero owns the bibliography. Nothing in the vault edits it.

```
Zotero ──(Better BibTeX auto-export)──> references.bib ──> Quarto ──> paper
   │
   └──(Zotero Integration plugin)──> literature/@citekey.md
```

## Citation keys

Format: `auth.lower + shorttitle(3,3) + year` — e.g. `smithdeeplea2024` for
Smith, *Deep Learning for Green Functions*, 2024. Set in Better BibTeX, so keys
are stable and reproducible rather than assigned per export.

## How to cite, by file type

| context                      | write            |
| ---------------------------- | ---------------- |
| An Obsidian note (`.md`)     | `[[@citekey]]`   |
| A Quarto draft (`.qmd`)      | `[@citekey]`     |
| Raw LaTeX                    | `\cite{citekey}` |

`[[@citekey]]` is the Obsidian form: it doubles as a wikilink to
`literature/@citekey.md`, so the note is one click away in the vault, and the
`obsidian` Lua filter turns it into a real Pandoc `Cite` at render time. Both
spellings resolve to the same BibTeX key.

## references.bib is read-only

It is generated by Better BibTeX's auto-export. **Never hand-edit it** — the
next export silently overwrites your change, and the bug looks like a citation
that "randomly" stopped resolving.

To add a reference: add the item in Zotero, then re-export (or let auto-export
fire). If the key still doesn't resolve, the export target is probably not
configured for this vault — that setup is per-vault and manual.

## Diagnosing a missing citation

A bad citation does **not** error. The link renders as plain text, the entry
never reaches the bibliography, and the reference list is quietly short. So
check explicitly rather than reading the PDF and assuming:

```bash
# every key cited in the vault
grep -rhoE '\[\[@[A-Za-z0-9_-]+|\[@[A-Za-z0-9_-]+' notes drafts \
  | grep -oE '@[A-Za-z0-9_-]+' | sort -u > /tmp/cited
# every key the bibliography defines
grep -oE '^@[a-zA-Z]+\{[^,]+' references.bib \
  | sed 's/.*{/@/' | sort -u > /tmp/have
comm -23 /tmp/cited /tmp/have    # cited but undefined
```

Anything listed is either a typo or an item not yet exported from Zotero.

The other failure is the reverse: the `.bib` has the key but the render still
drops it. That is a Quarto/filter problem, not a Zotero one — check that
`bibliography: references.bib` is in `_quarto.yml` and see the `pandoc` skill.

## Literature notes

`literature/@<citekey>.md`, one per Zotero item, generated by the Obsidian
Zotero Integration plugin.

- **Don't edit the metadata fields.** Edit in Zotero and re-sync; the plugin
  overwrites them.
- The body is yours — summaries, objections, links to `notes/`.
- A broken `[[@key]]` link often just means the lit note hasn't been synced yet.
  Re-syncing is a manual step inside Obsidian, not scriptable from here.

## Better BibTeX's JSON-RPC endpoint

BBT exposes `http://127.0.0.1:23119/better-bibtex/` while Zotero is running.
That is the hook for programmatic search and export — useful for checking a key
without leaving the terminal.

It only answers when Zotero is open. Anything built on it must degrade to a
clear "Zotero isn't running" rather than hanging or reporting an empty library
as a real result.

## Constraints

- The vault syncs to corporate OneDrive. Bibliographies are fine; PDFs of
  restricted material are not.
- Don't invent a citekey to make a render succeed. An unresolved citation is a
  visible problem; a fabricated reference is a much worse invisible one.
